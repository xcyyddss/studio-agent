# 上下文、长期记忆与故障恢复

Studio 关注的长期问题是意图、认识、假设与经验怎样演化和再用。保存一句“采用方案 X”，还不足以说明它在今天是用户偏好、临时选择、失败实验，还是某个仍有效思想的载体。历史上确实这样想过，与当前仍可将它作为依据，是两个不同判断。背景见 [设计动机与部件目的](design-rationale.md)。

上下文管理为这些判断提供可用材料，恢复机制保留尚未完成的责任。它们不能单独解决意义维护：摘要做得更短、记录保存得更久，都不能代替作者对原意、适用条件和新证据的解释。Studio 因而把模型调用、信息整理和业务承接分开保存。回答已经写入数据库，不代表议题已经处理；一个调用返回成功，也不代表后续议会、作者或父议题已完成工作。界面中的输入回执、执行记录和最终交付分别描述这些阶段。

## 几种长期信息各自承担什么

| 信息层次 | 保存与使用目的 | 不能据此推定的结论 |
| --- | --- | --- |
| 原始历史与执行档案 | 保留当时的表达、来源、版本和真实发生的动作，供回查与重新理解 | 旧记录中的说法现在仍正确 |
| 当前工作认识 | 记录本议题正在使用的约束、发现、假说、决定和开放问题，并允许修订、争议或退役 | 当前判断是不可再质疑的最终事实 |
| 议员经验与关系 | 将真实贡献中的抽象认识和场景观察连同条件、关系及修订保留，供后续问题形成 | 实现成功验证了全部假设，或实现失败使其抽象思想全部失效 |
| 容量整理记忆 | 原文装不下时，以来源范围和独立复核支持下一次调用，仍可取回原件 | 摘要已替责任者完成解释、采用或事实验证 |

经验维护与容量摘要是不同工作。前者判断一项经验应以什么条件和含义继续使用；后者组织已经获准的材料以便进入有限调用。抽象思想、具体实现和负结果的区分主要由认知加工、贡献评估和经验修订承担，不能交给压缩算法自动决定。当前这些记录按运行及角色作用域使用，新目标不会自动接入跨项目经验库。

## 输入和恢复的生命周期

用户回答与附件先提交到本地事务中，问题记为已回答，同时建立持续可见的输入回执。回执保留原问题、回答、接收议题、当前处理状态及模型说明的影响。网络失败不会删除回答，也不要求用户重复提交。网页重试同一份未修改的回答会复用提交标识，服务端据此去重。

作者与父议题每次获得 `input_obligations`。输出必须逐条使用 `input_uses` 说明实际用途、影响以及 `processed` 或 `followup`。尚需继续处理时，必须提出可执行后续工作或明确未解责任，不能同时宣称完成。调用封存后新到达的输入也会阻止过早交付。文件是否已真实读取，继续由附件版本、文字范围、页图送达和 `attachment_uses` 单独验证。

输入的送达、处理和分批范围各自有明确含义：

- 以前成功送达过的工具结果，如果仍是 `followup`，仍属于必需材料，不能当作可省略历史。只有已经完成处理的历史才可按普通历史规则选取或整理。
- `input_obligations` 只列本批实际展示且必须承接的输入。`deferred_input_obligations` 明列后续批次仍须处理的输入，本批不得登记它们的采用；软件核对各批合起来覆盖全部原始责任。父作者处理本批后以 `continue` 接收后续材料，不能提前交付或静止。
- 未送达输入优先进入批次，其后按最近成功送达时间安排未完成输入，避免反复讨论同一条 `followup` 挤掉后续材料。此排序不评价材料的认知价值。
- `followup` 可以等待任务包中已有的真实工具请求或问题，无须重复创建同一请求。等待的真实性以及调用期间是否已经返回，由工作流核验；没有真实后继仍会拒绝。
- 历史整理前后核对未完成输入身份。摘要不能删除这些责任，原件仍保留；每次封装、派发和结果导入都检查必需输入是否实际可见、是否重复。模型引用未知或未送达 ID 的结果仍会拒绝。

| 故障情况 | 系统行为 | 操作入口 |
| --- | --- | --- |
| 已确认的网络、连接或限流失败 | 保存原任务、错误和回执，按 5、15、45 秒退避，最多自动重试三次；更新所有当前调度引用 | 超过自动次数后，在执行记录或输入回执中重试 |
| 调用结果不明、进程异常中止 | 保留不确定状态，不自动重复可能已发生的工作 | 核对执行记录后明确允许重试 |
| 输出不符合协议 | 回滚未接受的语义修改，保留原输出；携带具体错误重新调用，最多两次自动修复 | 耗尽后查看错误，再修复或重试 |
| 任务包要求承接未展示的输入，或存在其他输入责任矛盾 | 调用前拦截；旧失败任务从该角色获准的原件和当前未完成责任重新封装，不要求模型猜测缺失输入 | 修正当前输入后重试或恢复调度；组装仍有矛盾时保留诊断，修复后恢复调度 |
| CLI 输入字符过大 | 识别 `input_too_large` 及数值边界；作者或父议题先重新做完整条目投影，未显示历史保留原件入口；必需内容仍放不下才整理 | 不重发相同超长输入；再次失败保留诊断 |
| 服务端报告 token 上下文过大 | 作者或父议题重新组装一次并按实际失败缩减，必要时使用经过复核的语义记忆 | 再次失败时可调整策略后重试或恢复调度 |
| 组装输入时已发现无法容纳，尚未创建 job | 保存已收到的结果、未完成的调度意图和可见诊断 | 网页“重新检查并恢复”，或 CLI `recover` |
| 正在整理历史时断网或重启 | 整理、复核也是持久任务；已通过的单元复用，未完成的继续或重试 | 同一套执行记录与恢复入口 |

网络重试使用原先封存的输入，不把通信失败解释成模型推理错误。真正的协议修复才附带审查意见。重试替换议会请求、评估、材料递送和记忆维护中的活动 job 引用，原始来源和旧执行记录不被覆盖。

任务包自身的问题使用 `input_rebuild` 说明；模型输出问题使用 `validation_failure`。系统先检查输入再决定是否需要模型修正。即使旧版本已耗尽模型输出重试次数，已确认的输入矛盾仍可重建；重建必须通过一致性预检，不能把同一个矛盾再次发给模型。作者和父作者的协议重试都重新组装当前授权范围，包含后来到达的信息；原先未获准的其他议题材料不会因重试进入上下文。原输出保留，但不能直接当成对新增材料的判断。

这类恢复不要求修改字符窗口，也不会自动接受被拒绝的原输出。网络故障次数与模型输出修正次数分别计算，执行结果不明仍不会自动重发。

## 容量不足时怎样整理调用上下文

每次调用都启动全新的临时 Codex CLI 上下文。长期增长的是 Studio 的资料与工作记录，不是一个持续追加的 CLI 会话。软件在组装当前角色的已授权材料时，执行以下过程：

1. **先确定是否需要整理。** 先组装完整协议、输出契约和已授权材料，按同一 token 计量规则检查容量。同次输入的完全相同历史正文只发送一份，记录分别保留。能容纳时直接使用原文，不因历史到达固定字符数而摘要。可回查历史先按完整条目选择；必需责任装不下才启动语义整理。
2. **划清整理范围。** 已明确处理的用户历史及其问题、同一议题同一角色已经接受的模型分析、决定和贡献，共同归入历史记忆。原始模型输出保留来源和历史性质，不因曾被接受就成为正确事实。未处理回答、当前约束、待办身份、权限、议题版本与决策 ID 继续作为工作状态保存；摘要不能取消这些责任。较长的必需正文也可以单独整理。摘要不会扩大角色原来的访问范围。
3. **分段保留原件。** 历史按交互记录排列，优先在记录或段落边界分段；过长的单条材料按精确字符范围拆分。每段保留原文、哈希、角色与议题作用域。整个整理计划记录连续的 start/end 范围，并逐字重建核验是否覆盖全部输入。相同作用域内未变的前缀可复用。正文哈希、议题/角色、协议版本和摘要目标共同确定缓存；无关兄弟单元的变化不使缓存失效。换行分隔符属于容器，追加记录不会改变上一个完整正文。每次使用的实际上游范围另行保存，权限不跨议题或角色扩张。
4. **独立语义整理。** `context_summary` 接收该段完整来源和认知协议，整理约束、决定、冲突、未解问题、早期方向及必要原话。数值、否定、权限、事实与猜想、修正先后不能被“更简洁”取代。篇幅目标不构成省略信息的授权。复核意见是编辑指导，不能把“上次遗漏、本次修复”等行政修订历史混进业务记忆。
5. **独立覆盖复核。** 全新 `context_review` 调用获得完整来源与候选摘要，逐项指出遗漏、歪曲、无依据添加和约束损失。程序拒绝范围不完整、引文不在原文中、或一边批准一边列出未解缺陷的结果。作者不能自己批准摘要。
6. **修复或保留原文。** 不通过的摘要携带反馈重写。两次修订仍不通过，就保留原文；没有 token 缩减也保留原文，并缓存为 `no_gain`，后续不重复尝试相同输入。不会为了进入窗口而强行截断。
7. **按需分层汇总。** 多段摘要仍使完整调用超限时，才继续整理并独立复核上层摘要；整包已能容纳就停止，不追求固定 10k 字符终点。单层缩减不足 10% 时保留已有有效结果，但不递归重写已经很密集的记忆；仍超限则明确要求分页或重构材料。每层保存子节点、输入范围、版本、复核结果和输出哈希，可以追溯到原始材料。原件始终保存。
8. **交给业务角色承接。** 当前任务包包含 `history_memory` / `semantic_memory`、来源引用和使用边界。`context_memory.uses` 记录哪些单元实际封入哪个 job；真正调用与承接还要检查执行回执及业务输出。需要精确文字、代码或数据时，角色使用 `context.retrieve` 按本包允许的引用回查原件。摘要不冒充附件或 PDF 原页的实际读取。

这包含两种不同的保证：字符范围核验是确定性的；语义等价与重要性判断由独立模型复核，仍可能出错。系统保留可回查原件、否定意见和修订轨迹，便于发现与修正错误，不把模型同意包装成数学意义的无损证明。

## 容量与关注窗口

所有角色，包括检索、议会、作者、用户协作、经验维护、语义整理和复核，使用 `gpt-6-astra`，`model_reasoning_effort="xhigh"`。不接受其他模型或 effort 的静默替换。

有三类不同的边界：

| 边界 | 默认值与含义 |
| --- | --- |
| 作者／父议题输入 | 完整调用包同时满足 token 预算与 CLI 的 1,048,576 字符硬边界；不是 120k 字符软上限。父议题可按不可拆的责任组分批，作者必须获得当前必需组 |
| 议员 A/B 窗口 | A 64,000、B 48,000、总计 128,000 字符；用于控制联想上下文，创建运行时可配置，不等同于物理容量 |
| CLI 窗口 | 默认显式请求 872,000 token；`model_context_window` 随封存任务派发，不依赖用户全局配置；可配置至本版本代码上限 1,050,000，但服务端是否支持该配置仍须实际验证 |
| 预检 | 使用窗口的 95%，预留输出 128,000、隐藏平台/工具 64,000、每张图像 32,000；同时计算 prompt 与独立输出 schema |
| 文本计量 | 使用随软件打包的 `o200k_base` 代理编码并增加 25% 余量；不把它声称为 Astra 的精确分词器。启动后首次使用时在本地校验并读取词表，不隐式联网下载。库或词表不可用时退回 UTF-8 字节上界，回执明确标记 |
| 摘要工作单元 | 默认来源块 64,000 字符，单元目标 24,000 字符；它们只控制整理工作分块，不触发整理，也不要求业务历史压至此长度 |

这些值是可审查的容量与质量起点，不是已证明的最佳注意力比例。本版本代码的容量上限常量为 1,050,000 token，这不是服务端能力验证；CLI 默认值、本地允许请求值与服务端真实接受能力应分开判断。每次回执记录请求窗口、自动整理阈值、计量方法、余量、实际返回 usage 和可见 compaction 事件。小输入调用成功不能证明接近最大窗口的调用成功。原生检索的多轮累计 usage 也不能直接当作单次上下文大小。

未映射的 tokenizer 是近似计量，隐藏输入及图像也不是精确测量。字符上限独立检查提示词字符串，不将字符和 token 互相等同。父题最终的动态输出契约和范围元数据也重新计量；执行器在启动 CLI 前再检查旧版封存输入的字符长度。错误回执只提取公开的容量数字，不把任意 stderr 内容复制到界面。服务端容量拒绝会触发一次针对整包的缩减重建；再次失败保留诊断，不无限重写。CLI 的自动整理属于宿主机制，不能替代 Studio 的原件、覆盖与承接记录。


创建时可提供策略，例如：

```json
{
  "model_context_tokens": 872000,
  "effective_window_percent": 95,
  "output_reserve_tokens": 128000,
  "platform_reserve_tokens": 64000,
  "image_reserve_tokens": 32000,
  "token_margin_percent": 25,
  "source_chunk_chars": 64000,
  "summary_target_chars": 24000,
  "preparation_parallelism": 6
}
```

```powershell
python -m studio_runtime --data-root studio-data create --goal-file goal.txt --context-policy policy.json --council-limits council.json
```

`council.json` 需要 `abstract_chars`、`scenario_chars`、`total_chars` 三个正整数字段；窗口在该次运行中固定，保存在 CONFIG 中，不受旧默认最大值钳制。选择记录会明确记载未入窗材料，原件可另行请求。

```powershell
python -m studio_runtime --data-root studio-data recover RUN_ID --context-policy policy.json
python -m studio_runtime --data-root studio-data run RUN_ID
```

`recover` 合并并验证新的上下文策略，重新检查阻塞与容量重组；CLI 中再运行 `run` 启动调度。网页恢复按钮会同时启动调度器。过小的物理容量、无法安全拆分的当前约束或无法充分压缩的材料会保留为明确阻塞，需要调整输入组织；不会通过丢弃事实获得“成功”。

## 保存与检查

日常调度状态与不可变大正文分开保存：`state_bodies` 按内容哈希保存提示词、完整快照、契约和计量报告，常用状态只保存引用与调度字段。引用在软件内部解析，不送给模型；来源 JSON 与内部引用类型区分。正文、状态指针、结果导入和后继意图使用同一事务，拒绝或崩溃不能留下半条语义修改。

`work_reports` 按议题和角色索引有效历史的语义字段，原始完整输出仍在 `results`；`artifact_headers` 保存路径、来源、长度和文件字节哈希。当前工作读取相关新结果与必要材料，不通过把空余窗口填满旧正文来决定关注范围。旧文件目录仍可直接绑定给专项认知加工，原文可以按明确范围取回。

状态查询采用 SQLite 只读快照，不持有监督锁，也不读取全部历史提示词。网页收到状态投影与产物目录；执行器查询待执行工具时只取对应请求。产物发布有持久回执，普通 tick 不再反复重写全部文件。归档不是删除，也不限制探索轮数；长期磁盘清理仍应通过显式备份和任务管理进行。

USER 的无效资产提议单独隔离，保留原结果、具体错误和来源，不把其状态自动降级后强行接受；同一包的有效认识仍可保存。整批契约修复耗尽后隔离该批，后续新观察可继续处理，页面可查看并重试被隔离的调用。隔离不意味着旧观察已经完成处理。只有完整真实证据链才能支持引导方法；runtime 事件记录实际产物提交和版本，不能冒充用户效果。

`workflow.db` 保存输入回执、原件快照、整理计划、语义单元、逐版复核和任务承接记录；每次调用目录保存真实 prompt、schema、命令、结果与 receipt。检查点包含这些内容。来源不覆盖，经验和工作历史会持续占用磁盘；当前机制解决长期上下文组织与恢复，不承诺无限磁盘或任意规模数据库的性能。

模型容量与支持的推理档位见 [OpenAI 的 GPT-6 Astra 模型说明](https://developers.openai.com/api/docs/models/gpt-6-astra)。

CLI 窗口字段见 [OpenAI 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。
