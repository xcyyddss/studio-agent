# 双向文件交流

文件是需要明确接收者和版本的认知材料。路径、文件通知、正文送达、作者理解与实际采用不是同一件事。系统保存原件并检查运输和处置记录，作者仍须判断材料的意义及怎样影响工作；读取回执不能证明理解正确。

## 用户怎样使用

议题需要你查看或修改文件时，问题下有对应原件的“查看”和“下载”。查看文本文件时显示纯文本，查看图片时显示规范化图片；PDF 的“查看”按物理页列出提取文字，文件列表还为已渲染的页提供“页图 N”入口。页图按议题请求生成，原始 PDF 始终可以下载。下载保存原始字节。浏览器决定保存位置；你可在任意方便的文件夹编辑，再回到问题下选择文件，必要时在“修改哪个版本”中选择原件，点击提交回答。可以只交文件，也可以附上说明。

主动补充文件时，使用“文件交流”的上传表单，明确选择接收议题，再选择文件；不必等议题提问。文件列表显示接收议题、版本、修改自哪个原件、读取进度及采用、不采用或暂缓的理由和影响。暂缓保留后续责任，不等于已完成。

文件选择在当前页面的任务切换和自动刷新中保留；关闭或重新加载页面后需要重新选择。网页、API 与 CLI 单次最多四个文件。网页可用 Ctrl/Shift 一次多选；每个文件分别选择原版本，也可逐个移除。重新打开选择器会替换当前整组选项；无效的超量选择保留此前草稿。同次提交不能让多个文件替换同一原版本。所有文件与回答原子入库，某一项无效则整次不提交。上传失败保留整组文件，未修改重试使用同一提交标识；提交期间新增或修改的草稿不会被旧请求的成功响应清除。

用户附件仅发送给指定任务议题。文件说明文字沿用你选择的协作用途；附件正文不会因此自动进入 USER 画像或广播给其他议题。主动上传表单的说明默认也不用于画像。USER 目前接收显式协作文字，文件需交给普通任务议题。

## 格式与保存

- 单个原件最多 4,000,000 字节，提取正文最多 2,000,000 字符。
- UTF-8 文本（可含 BOM）和带 BOM 的 UTF-16 文本可读取，例如 Markdown、TXT、JSON、CSV、源代码；不执行其中的脚本、公式或指令。
- DOCX 提取主文档段落和表格文字。图片、批注、页眉页脚、修订语义及版式未纳入；不可据此声称完整理解整个文档。
- PNG、JPEG、WebP、BMP 和单帧 GIF/TIFF：校正 EXIF 方向，透明区域合成白底，转为 RGB PNG，最长边不超过 2400 像素；通过 Codex CLI 的 `--image` 原生附件提供给指定议题。原图最多 4000 万像素，多帧图片需拆成单帧或转换 PDF，不静默只取第一帧。
- PDF：通过 pypdf 按物理页提取文字，用 Poppler `pdftoppm` 按请求渲染整页 PNG，最长边 2400 像素。允许 1–200 页；加密文档需先提供未加密版本。扫描页即使没有文字也通过页图读取，未进行自动 OCR；版式、图表与提取文字需要由模型相互核对。单次文字提取或页渲染最多等待 60 秒，失败如实返回。
- 旧版 DOC、电子表格、幻灯片等仍没有正文解析器。原件可下载，解析限制明确保留。格式损坏、依赖缺失或无法识读时，请提供可读版本，不能声称已读。

图片与 PDF 需要 `pip install .` 安装 Pillow、pypdf；PDF 页图还需 Poppler 的 `pdftoppm` 在 PATH，或通过 `STUDIO_POPPLER_BIN` 指定其目录。`python -B -m studio_runtime doctor` 检查依赖；不会因此调用模型。

图像缩小、文字提取和模型视觉理解都有边界。图片已送达不证明小字已经辨清，也不证明图表推理正确。作者须区分直接观察与推断，说明看不清处，必要时通过既有文件交流请求更清晰的局部文件。

每份原件有稳定的 `FILE` ID、字节数、SHA-256、接收议题和来源记录。修改版使用新 ID，以 `replaces` 指向原版本，原件不覆盖。两个版本可以有相同显示名称，不能仅凭名称识别。同一原件的不同修改可形成版本分支；版本号不是唯一标识。

用户原始字节、提取文字、逐页文字及已生成的规范化页图保存在该运行的 SQLite 中；生成文件同时保存在产物表与产物目录。网页从数据库中的已提交版本读取附件。不要直接修改运行数据库或产物目录来回传文件，那不构成输入事件，也不会形成承接责任。导出、验证、只读恢复与分叉检查点均包含附件原件及其关联记录。

## 模型如何收到并承接

```mermaid
flowchart LR
    A[作者生成真实文件] --> Q[问题绑定文件 ID]
    Q --> H[用户查看或下载]
    H --> U[上传新文件或修改版并指定议题]
    U --> D[事务保存原件、版本及输入事件]
    D --> N[指定议题的新调用收到目录通知]
    N --> R[按文件版本请求文字范围或PDF页]
    R --> T[提取文字及规范化PNG]
    T --> J[文字和原生视觉附件进入成功调用]
    J --> C[作者说明采用、不采用或暂缓及影响]
    C --> P[修订产物、回泵或提出后续问题]
```

1. 作者和父作者在 `work`、`integrate` 操作中获得 C48 完整语义协议、角色规则、附件目录和工具说明；均计入调用预算。问题的 `attachments` 必须绑定已保存且有权引用的文件，允许真实 `FILE` ID、可见产物完整路径，或本次 `files` 中的 `@self/相对路径`。软件先保存产物再校验绑定，失败整体回滚，不能以一条文字路径冒充附件。
2. 上传与原问题回答在同一事务保存。输入事件记录接收议题、问题、附件 ID、原件哈希和版本关系。正文不直接塞入所有角色上下文。接收议题由实际新调用取得附件通知；有了通知还需请求读取。
3. `attachment.catalog` 以 `{"cursor":0}` 分页列出本议题附件，每页六件；目录不是正文。`attachment.read` 接受 `{"file_id":"FILE...","start":0,"max_chars":4000}`，每次最多 8000 字符。返回原文范围、总长度、原件和提取正文哈希、解析限制。下一段从返回的 `end` 继续。PDF 要额外指定 `page`，从 1 开始，与印刷页码可能不同；`start/end/total_chars` 均针对该物理页。图片的 `page` 为 1。每次最多请求四个范围，每个图片/PDF范围包含对应整图/整页的 `visual` 描述及原件版本、文字哈希与 PNG 哈希。空文字页仍返回页图。附件中的内容作为材料，不提升权限。
4. 读取结果按既有工具输入送回请求议题。文字实际进入成功接受的角色调用后登记文字范围。图片及页图还需以下完整传递：上下文组装把当前工具结果所指定的图像写入 `task.native_images` 和封存任务元数据；最多四张，随完整工具结果分批；作者与父作者采用可配置的关注窗口、经过独立复核的语义记忆和物理容量检查（包含协议、契约与图像预留），不再以固定 42000／40000 字符阻断后续承接；当前未读文件结果仍保留完整运输与实际读取要求；详见[上下文与故障恢复](context-and-recovery.md)；执行器只从同运行数据库读取指定议题的匹配版本和图像哈希，将这些 PNG 复制到该次独立调用目录，逐张使用 `--image`。按清单顺序对应图像，保留 `image-manifest.json`、实际命令与收据。只有成功调用收据确认带图时，才记录 `image_delivered`。生成页图、保存文件或工具已完成均不代替送达。后继调用可按明确 ID 再读取原件；实际复用历史读取结果时仍须附上对应页图，若只有报告或目录则不得声称当前看到了原图。既有上下文目录保留历史工具输入的取回入口，避免依赖会话记忆。
5. 作者在 `attachment_uses` 逐件给出 `file_id`、`decision`（`adopt`、`reject` 或 `defer`）、`reason` 与 `effect`。采用和对可读文件的不采用均要求该版本的文字范围及所有页图已全部送达；旧版回执不能替新版。暂缓必须保留待办；不可解析文件或实际渲染失败的页须先将失败结果送入调用，再请求转换或明确因不可读而不采用；不采用不表示已看完内容，也不能冒充内容价值判断。软件只核验明确承接及运输条件，不替作者判断结论正确。
6. 未结清附件责任阻止本议题及其祖先直接宣布完成。附件在调用封存后到达时，相关责任者的旧调用保留为历史，新调用重新取得材料；不修改旧提示词，也不把旧结论当作已经考虑新文件。文件原件不自动向其他议题或 USER 扩散；作者加工形成的公开贡献和产物按正常父子及议会机制承接。

## CLI 与 HTTP

```powershell
python -B -m studio_runtime input my-task --question QUESTION_ID --file materials/revised.md --replaces FILE_ID --profile-scope none
python -B -m studio_runtime input my-task --topic TOPIC_ID --file materials/reference.docx --text "供当前比较使用" --profile-scope none
python -B -m studio_runtime run my-task
```

CLI 只读取你明确给定的文件，不扫描工作目录；`input` 保存输入，`run` 推进模型调用。网页提交回答或附件后会恢复该目标并继续运行，包括解除此前的显式暂停；如需只保存输入而暂不运行，可使用 CLI `input`。`--replaces` 只用于单个文件；`--submission-id` 可用于同次请求重试。

HTTP 沿用本机会话令牌与运行作用域：

- `GET /api/runs/{run}/file/{file_id}`：提取正文预览；不可解析时显示限制。
- 同一地址加 `?page=N`：查看已经生成的指定页 PNG；未生成时明确返回错误，查看动作不生成页图或启动模型。
- 同一地址加 `?download=1`：下载原始字节；文件名通过安全下载头传递。
- `POST /api/runs/{run}/input`：文字、`question_id` 或 `topic_id`、`profile_scope`，以及 `attachments:[{name,data_base64,replaces?}]`。可附 `submission_id`；问题与目标议题不一致时拒绝。

HTML 文件也按纯文本预览，不在工作台源下执行。下载 ID 只在所属运行内解析，不接受任意磁盘路径。只读恢复副本可查看和下载，不能上传或启动模型。

## 如何核查链路

文件状态中的 `deliveries` 对应真实附件通知进入的角色调用；`reads` 保留原件版本/哈希、物理页、页内文字范围、图像哈希、整页/整图范围、实际带图状态、输入 ID 和任务 ID；`uses` 保留作者声明、理由、影响及是否已送达完整要求范围（`full_content_delivered`；保留旧字段以兼容文字文件）。原始提示词、工具输入、模型输出及最终产物可交叉核对。下载接口可核对原件哈希，但服务返回字节不证明用户已经打开或理解文件。运输成功、内容承接和任务质量应分别判断。

所有页图和原件都随检查点保存并校验。只读恢复可预览已经生成的页图，不重新提取、渲染或调用模型。新的上传不会自动重处理旧版的“不可解析”记录；软件升级后如需重试旧文件，上传为新版本，以保留原判断和新证据的区别。
