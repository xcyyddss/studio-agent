# 用户任务的协调与交接

多个独立议题可能都发现自己缺少同一种用户证据。局部窗口中没有答复，不能直接推断用户从未做过这项工作。系统将“提出问题”“批准向用户发布”“收到答复”“交接报告”“接收者读取和承接”分别保存。

## 发布前协调

子议题输出的 `questions` 先记为 `proposed`，由其父议题在普通父调用中处理。网页不把它当作待答问题，也不登记已经向用户展示。父调用取得 `task.interaction`：

- `directory`：本题、直接子题及祖先提问的状态目录；不含其他议题的答复正文。
- `review`：分配给本父议题的具体提案，含绑定的真实文件描述。
- `handoffs`：本题负责、尚未结清的交接。
- `snapshot`：提问状态及本题输入到达状态的封存指纹。

父议题在 `question_decisions` 中逐条给出 `publish`、`reuse`、`withdraw` 或 `escalate`。发布须说明独立需要；复用须引用自己已发布或已收到答复的问题；撤回保留原问题及理由；需要祖先协调时沿真实父链上报，原提问议题不变。语义上的相同与不同仍由模型判断，软件不把关键词相似当作已证明重复。

父调用开始后若有新答复或提问状态变化，旧调用的发布决定不会直接展示给用户。实际产物保留，该提案以最新状态进入下一次父调用复查。ROOT 自己提出的新问题同样检查输入是否在调用期间改变。无需为每个提问另建一个审查模型角色。

已有受众限制优先：若引导材料明确只授权当前作者和 USER，不能为了协调把其衍生问题交给父角色。此时保留原来获准的直接提问路径，登记 `scope_limited_direct`，父目录仅显示不含正文的状态；这一例外不能声称已经完成跨议题内容判重。交接同样检查来源问题是否授权具体接收者。

## 依赖及实际交接

`question_handoffs` 每项包含：

| 字段 | 含义 |
|---|---|
| `question_id` | 当前可见问题 ID；本次新问题可用 `@self/question/0`，零起点 |
| `recipient` | 明确的后代议题 ID，或本次采用的候选 ID（解析为实际新子题） |
| `reason` | 这份答复为什么是该子工作的依赖 |
| `summary` | 有来源的父议题报告；尚待答复或读取准备时为空 |
| `attachments` | 本题撰写的报告版本；真实 FILE ID 或本次 `@self/文件路径` |

注册依赖时，接收者得到一个模型来源的协调输入，知道已有用户任务及等待关系，可以继续不依赖答复的工作。收到答复后，软件唤醒负责交接的父议题；父议题须先取得所需阅读依据，编写交接报告，或安排实际准备动作。不能用无后继的 `continue` 把依赖遗忘。

用户原始答复和上传附件不会经此接口自动转发。父议题的加工报告明确标为模型报告，并保留来源答复 ID、文件版本与哈希。交接附件在接收者处具有独立读取和承接记录；原议题读过不等于新接收者读过。接收者须通过 `input_uses` 处理协调输入，并通过 `attachment.read` 与 `attachment_uses` 读取、采用或有据地不采用报告文件。

交接完成只表示报告已送入接收者的待办，不表示工作已经完成。接收者的未处理输入和附件责任仍会阻止过早结束。被复用的重复问题转为 `linked`，报告送达后变为 `resolved`；被撤回的问题为 `cancelled`。撤回来源任务也会取消尚待交接的依赖并通知接收者。

文件型答复须先完成原接收者的读取与处置，或留下实际不可读结果及有据的不采用，才能据此交接；不能仅凭文件目录编写已验证结论。用户明确上传修改版时，关联交接重新进入待整理状态，记录新输入和对应版本；旧报告保留，新接收者也不会继承旧版的阅读回执。

## 接续与检查

记录保存在现有 `workflow.db`，不删除旧问题、答复、输入、调用或原件。新字段在实际使用时追加；旧任务仍按其封存的 schema 校验。旧调用产生的新问题也经过发布流程，而不是借旧协议直接绕过协调。

网页的待答区只呈现已发布问题；诊断记录中可查看内部提案与交接状态。问题重用的语义判断、交接报告的充分性仍可能出错；可通过保存的源答复、交接产物与接收者承接记录复核。程序保证事务、边界、版本和未完责任，不声称自动判断每个诊断是否相同。
