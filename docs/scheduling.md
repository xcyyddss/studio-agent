# 调度、反馈批次与调用用途

调度服务于认识的形成与承接。父作者承担本层目标的综合判断，子作者提供独立加工后的认识、反例、条件和产物；这些结果可能改变父题的问法，而不只是填满原先拆出的任务。实践反馈需要重新进入问题空间，父作者才有机会依据它修正下一步。设计背景见 [设计动机与部件目的](design-rationale.md)。

有限反馈批次为这种综合保留明确范围：哪些子责任应返回，哪些实际材料和评估已经到达，哪些仍不可当作已知。它既减少由完成先后带来的重复父调用，也避免父作者仅凭最早返回的局部结果就把整体认识固化。若新的反证、用户输入或阻塞需要立即处理，允许提前综合，但缺席责任仍须保留。批次齐备只提供判断条件，不代表各贡献已经相容或整体目标已经完成。

并发控制决定能同时派出多少已满足前提的调用，不改变某项判断所需的前提。系统不会保证不同并发设置生成完全相同的模型答案：用户新输入、阻塞与紧急通知可能改变实际可见的信息时点，模型本身也存在生成差异。调度顺序和批次机制不能代替父作者对具体结果的解释。

## 运行与并发设置

每个目标的 `app.json.scheduling.max_workers` 保存 1–32 的整数，默认 6。网页创建表单和运行页均提供设置；`POST /api/runs/{id}/scheduling` 在本机来源检查与会话 token 验证后修改。`--workers` 和 Windows 启动脚本的 `-Workers` 设定新目标默认值，已存在目标继续采用自己的保存值。

设置更新与调度使用同一目标的监督锁。下一次派发读取新值；已封存输入、已开始的进程及结果不变。降低上限时允许当前在途数暂时高于新值，等待它自然下降后再补充。SQLite 领取事务统计 leased/running，多个监督进程也不能通过同时检查绕过上限。每个目标拥有独立队列，多个目标的总并发可能超过 6。

摘要准备自身最多同时准备 6 个单元调用；这是准备任务数，实际派发还受到目标并发上限约束。议员数量、议题数量与同时调用数是不同指标。

## 父议题何时获得回传

1. 一次父决定实际创建或重铸子题后，将这些子题的 ID、版本及纠正 epoch 保存为一个有限批次。后来其他批次生成的子题不会追加入这批，使等待对象无限增长。
2. 子作者完成后仍需独立贡献评估。对应回传及其评估齐备，才进入父议题的 `new_returns`；摘要复核或经验维护不是这项贡献评估的替代品。
3. 同一监督 tick 中已到达的执行结果、以及本轮可立即取得的工具结果先逐条持久提交，随后统一推进调度。某一结果无效不会回滚其他已经导入的结果；进程中断后可幂等接续。尚需独立模型或外部回答的工具请求继续保留依赖，不为合批假装已经返回。
4. 普通反馈等待同批子责任达到 ready、consumed 或 superseded。只等待自己的批次，不等待无关分支。一次父任务封存了哪些 `return_ids`，就只允许处置这些 ID；期间新到达的结果留给下一次。
5. 被替代的版本保留来源和历史结果，不当作当前版本已完成。批次所有槽位已消费或被替代后关闭。

提前处理的条件：

- 父题有尚未处理的直接用户输入或工具结果。
- 存在需要它处置的上报、已完成的议会咨询，避免等待依赖于它自己决定的下游工作。
- 子作者使用 `parent_notice.priority=urgent`，明确说明当前反证、风险或依赖为何不能等到兄弟题完成。这个通知不代表父题已接受结论，也不取消独立评估。
- 同批子题因真实用户问题、失败调用或显式调度阻塞受阻，可以先汇合已到部分。

`feedback_batch` 列明原因、各子题版本、已到回传、仍在途责任和阻塞依据。提前处理不解除缺席责任，也不能越过已有的终止校验。受阻状态解决后，剩余回传继续进入后续批次。

等待只使用已保存状态，不额外调用模型判断“现在该不该调用模型”，也不依赖一个任意的短延时来猜测是否还有返回。

## 等待、真实唤醒与阶段交付

探索性目标可能需要用户继续理解问题、获得外部事实，或观察一次实践的结果。此时保留可用阶段成果与真实等待条件，比为了保持运行而反复生成细节更有价值。新信息到达后可以重新打开认识；已有产物并不要求把仍未明确的问题强行宣布为完成。

等待记录绑定真实问题、交接、工具、恢复事项或父责任内的在途工作。调用前已交付/取消的交接属于历史；只有调用封存时仍待办、应用时已经解决且有真实结果依据的变化，才触发补充调用。作者封存新任务包时消费当前刷新标记，新信息在封存后到达则留给下一次。反复轮询与重启本身不构成新信息。

`status=checkpoint` 让作者回传可用的阶段 ans、con、contributions，同时保持依赖等待。阶段回传也经过独立评估，由父明确承接；`new_returns.delivery_kind` 为 `checkpoint`，不能当成整个子责任已完成。原反馈批次保持未完成槽位，直到最终回传或版本被明确替代。评估导入不会覆盖作者的等待或后续工作状态。

父作者可用 `action=checkpoint` 交付实际阶段文件，同时保留等待依据。ROOT 的交付记录为 `partial`，网页标明“阶段交付 · 仍有依赖等待”；正式 `deliver`、作者 `complete` 仍须通过输入、附件、工具、交接等完成检查。仅有文字“阶段完成”不能解除依赖。

## 无增量回执与历史

工作记录分为四个相互关联的部分：`phase` 说明当前阶段交付和验收条件；`working_knowledge` 保存有来源、可修订的事实判断、假设、决定和开放问题；`last_delta` 保存本轮实际登记的变化；输入回执及依赖账本决定后继是否有真实触发。认识改变必须指向当前可见版本，旧版本保留；无更新不清空旧认识。模型声明“有进展”与软件实际记录了哪些变化分别保存，不把声明当作创新证明。

`progress.kind=operational` 表示交付材料、登记依赖或处理执行状态；作者可以提交没有认知贡献的操作型 checkpoint，软件不为它制造贡献评估。`advance` 保留认知结果，`no_change` 仅保留等待回执。条件性义务用 `obligation_decisions` 明确解决或撤回，不能只在新摘要中反复提到而永久挂起。

每次结果用 `progress` 说明是否产生进展。`no_change` 仅适用于有真实依赖的等待；程序拒绝同时新增贡献、工具、文件、问题、义务、阶段变更或处置决定，也不允许借此重新打开已处理输入。`advance` 保留独特成果，包括负结果、未知和不同解释。

同一版本连续的无增量声明和完全相同输出在工作上下文中折叠为回执计数与范围；原始结果、输入、出处始终保存在数据库。折叠不是模型语义总结，也不证明无增量声明正确。`history.catalog` 列出本角色、本议题已采纳的历史 job，`history.read` 按 job 和字符范围取回原文；无法跨角色或跨议题取历史。新认识不按相似度自动删除。历史按创建时间排序，避免 JOB.100 排在 JOB.99 前面。

已处理输入在无增量报告中的再次引用不产生新的 USER 学习事件。完全相同的条件性未知只保存一个当前义务及再次确认计数，完整表述仍可在原始输出追溯。实际新观察、改变的用途和新判断继续正常承接。

## 候选生成与有限核对

议员固定窗口装不下本次必需资料时，先完整分段、语义整理并独立复核，再给每位议员封装自己的资料表示。不同议员的准备范围保持隔离。已开始的准备与生成按持久意图接续，不重复创建同一议员的调用；摘要不能保全必要条件时留下明确阻塞，不能只送第一片或借另一独立调用“读过后半片”。`delivery_prepared`、`consumer_processed`、`delivery_acknowledged` 分别表示封装完成、收到了实际议员结果、父题登记了实际用法与影响，均不单独证明材料充分。

同一议员对同一次回传的多项贡献在输入可容纳时合并评估；每项仍须独立给出判断、条件和经验，程序拒绝漏项及重复索引。不同议员不合并上下文。超限按实际容量拆分；同一调度周期不重复评估。操作者明确请求修复材料交付并重新评估时，创建有来源的新周期，保留旧判断；已有该回传的重评正在运行时不能重复创建。该议员当前评估批次结束后再整理新经验，避免每完成一项就重新整理一次不断扩大的经验库。

议会生成返回 `proposed`、`no_new_direction` 或 `insufficient_material` 及理由。父作者收到真实 `inquiry_results`，在 `inquiry_uses` 中明确说明承接；空候选不能被略过。咨询关闭仅表示候选生成及处置已完成，不能宣称文件、责任或全部缺口已核对。

需要专项核对时使用 `cognition.process` 的 `bounded_review`，显式提供非空 checklist，每项绑定选中的实际来源。程序验证来源指针和哈希、逐项结果覆盖，结果通过原工具请求返回责任者并要求 input_uses 承接。文件名、目录或摘要不冒充原件；不足时返回 `insufficient_material` 及剩余需要。详见[认知操作协议](cognitive-protocols.md)。

若核对对象是同次输出刚生成的文件，可请求 `context.retrieve` 的 `path=@self/文件名`，取得真实原文、范围与哈希。此快捷路径只允许读取该调用实际保存的产物，不允许借路径读取其他调用或其他议题。其他来源仍使用当前调用获准的封存指针；读取失败会作为失败结果交回责任者，不能冒充材料已经送达。

历史文件通常仅在上下文中保留版本目录。`cognition.process` 绑定该目录条目或其 `/content` 指针时，软件按封存路径、来源 job 和字节 SHA-256 直接加载精确正文，并将读取范围与来源一起交给加工者；不增加一次只负责转述文件内容的作者调用。文件哈希采用 UTF-8 文件字节，任务包和 JSON 对象的内容摘要另行标识，不能互相代替。

## 内部请求与阶段交付

作者缺少直接父题的材料、决定或执行条件时，以 `internal_requests` 登记稳定 key、类型和实际需要。登记请求与提交阶段成果属于同一事务，因此不再要求先存在一个外部问题才能提交阶段回传。父题每个可见请求都要 `deliver`、`decline` 或 `defer`：交付可以绑定自己的真实公开文件版本；拒绝要有明确报告；延期必须引用现存问题、工具或上级请求，不能以“以后再看”形成永久死等。

父题正式回应形成指定子题的输入义务，绑定文件的真实正文随之递送。只有接收者实际处理该输入后，依赖才成为 consumed。已有内部请求的正常答复不废弃在途等待调用；旧调用可保留局部成果，软件识别封存后发生的依赖解决，并让下一次调用处理新输入。修改责任的新交接和用户纠正仍保留各自的失效规则。

阶段交付不解除其余依赖。父题可以用 `stage_artifacts` 指向已经保存的可用版本，无需重写文件。新事件会恢复相关责任；没有变化的轮询、重启、旧记录或行政维护完成均不能单独制造认知调用。系统没有探索轮数截止。

## 哪些工作不会自动唤醒 ROOT

用户协作审阅和经验关系维护各自消费新事件、新经验。完成一次行政整理不等于业务决策已有新内容，因此不自动将 ROOT 标为 dirty。其有权限的经验与协作建议进入后续正常选材；明确 `user.consult` 请求仍通过原工具依赖把实际结果交回请求方。画像的私有内容不会因调度通知而广播。

行政整理不作为业务交付的等待门槛。若交付时它仍在运行，整体状态可以暂时 active；整理完成后恢复 ROOT 已成立的交付/静止状态，不再补一次父调用。经验整理绑定实际经验 ID，ROOT 的普通交付换版不会使它失效；用户纠正带来的 epoch 变化仍使旧调用失效。真正的 `user.consult`、未承接输入和其他业务依赖继续阻止越过完成条件。

这不意味着省略独立评估或语义复核。需要区分：

| 调用 | 作用与触发 |
| --- | --- |
| member | 某次议会咨询的独立 q×I 提议 |
| author / parent | 议题加工、子题组织与成果承接 |
| assessment | 对实际新贡献作独立判断，并形成带条件经验 |
| user_review | 加工尚未处理且获准的用户交互事件 |
| memory_review | 整理新经验与既有经验的关系；允许无修改 |
| context_summary / context_review | 完整业务输入装不下时的语义整理及独立覆盖复核 |
| processing | 实际请求的认知加工或原生联网检索 |

同一议题可能产生许多调用，但重复同一无变化材料的整理、没有业务原因的父调用、无收益的递归摘要不应成为默认循环。

## 可检查证据

- 目标状态中的 `feedback_waves`、`feedback_wait`：批次、预期子版本、等待原因、派发记录。
- 每个父 job 的 `metadata.feedback_batch`、`return_ids`：实际封存的判断范围。
- `context_memory.units/plans/uses`：原件覆盖、实际上游、复核历史、无收益结论、进入哪个业务调用。
- 调用 `receipt.context_capacity`：显式 CLI 窗口、预检、实际 usage 与宿主可见整理事件。预检不是服务端容量验证。
- 执行队列与输入回执：模型返回、语义导入、用户回答承接各自独立。

这些机制支持真实贡献的接收、版本和未完责任的保留，并降低可避免的重复工作。它们不证明某个并发数或摘要比例能自动得到最佳认知效果。还应检查实践结果是否改变了问题理解、负结果是否保留了正确边界、父作者是否实际处理了不同解释，以及用户能否依据成果继续思考；调用数量或任务完成率不能独立回答这些问题。
